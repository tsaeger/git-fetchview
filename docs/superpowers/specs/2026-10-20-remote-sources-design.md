# Remote sources

Status: draft for review. Nothing here is implemented.

## Why

The tool exists for Linux kernel work. The kernel has hundreds of repos worth
looking at: subsystem trees, maintainer trees, and the trees behind pull
requests that Linus merges. A clone has only a few of them as remotes. Today
the picker only lists what `git remote -v` shows, so most of what matters is
out of reach.

This design adds a way to collect those repos into files, and makes the picker
list them next to the real remotes.

## Goals

- Collect remotes from several places with one workflow: merge commits in the
  current history, the `MAINTAINERS` file, and a plain URL list. More sources
  (lore.kernel.org first) can be added later without touching the picker.
- Keep the collected set out of `.git/config` and out of `git remote`. It can
  be large, shared between clones, and generated by scripts.
- Show the collected remotes in the existing picker, filterable with `/`.
- Work interactively (browse and choose from hundreds of candidates) and
  non-interactively (re-run from a script).

## Non-goals

- lore.kernel.org as a source. It needs network access and a choice of query
  method. It is deferred, but the source interface must not block it.
- Remembering which branch or tag a pull request named. Merge subjects carry
  it (`Merge tag 'net-6.x' of ...`). We drop it for now.
- Creating real `[remote]` sections or refspecs.

## Concepts

**Entry**: one repo URL, an optional label, and a set of tags.

**Remotes file**: a text file of entries.

**Registry**: the list of remotes files that `git config` points at.

**Source**: something that scans and produces candidate entries. The first
sources are `merges`, `maintainers` and `url`.

## Configuration

Settings stay in `git config`. One new multi-valued key points at the files:

```
fetchview.remotes = <path>
```

- `~` is expanded.
- A relative path is resolved against the directory of the config file that
  contains the value, the same rule as `include.path`. In `.git/config`,
  `fetchview.remotes` means `.git/fetchview.remotes`.
- The usual system, global and local hierarchy applies. Values from every level
  are used, in the order git reports them.
- Read with `git config --type=path --show-origin --get-all fetchview.remotes`
  so the origin file is known for resolving relative paths. Values that come
  from the command line origin are ignored.

For linked worktrees the local config and the default file both live in the
common git dir (`git rev-parse --git-common-dir`), so all worktrees share them.

## Remotes file format

One entry per line, fields separated by a tab:

```
# from MAINTAINERS, 2026-10-20
https://git.kernel.org/pub/scm/linux/kernel/git/netdev/net-next.git	netdev/net-next	maintainers,merge
```

| field | required | meaning |
|-------|----------|---------|
| url   | yes      | what git fetches from |
| label | no       | short name for the picker; derived from the URL when empty |
| tags  | no       | comma-separated, e.g. `maintainers`, `merge`, `manual` |

- Blank lines and lines starting with `#` are comments and are preserved.
- A line that fails to parse or validate is skipped with a warning that names
  the file and line. It never stops the picker.
- Files are untrusted input. They may be shared or generated, so every URL is
  validated on load, not only on import.

### Label

When no label is given, use the last two path segments with a trailing `.git`
removed: `.../kernel/git/netdev/net-next.git` becomes `netdev/net-next`. A path
with one segment becomes `host/segment`. Labels need not be unique. The picker
shows the URL beside them.

## URL rules

A URL is accepted only in one of these forms:

- `https://`, `http://`, `git://` or `ssh://` followed by a non-empty host
- scp-style `[user@]host:path`, where the part before the first `:` has no `/`

Everything else is rejected and counted in the summary. That covers:

- transport helpers such as `ext::` and `fd::`
- `file:` URLs and bare paths
- anything starting with `-`
- anything containing whitespace or control characters
- an empty host

Passwords in `scheme://user:password@host` are removed on import, reusing
`git::redact_url`.

### Identity

Two URLs name the same repo when their keys match. The key is the host
(lowercased) plus the path, with trailing `/` and `.git` removed. For
`http`, `https` and `git` the scheme is ignored, since the kernel uses `git://`
and `https://` for the same trees. `ssh` and scp-style URLs keep their user
and scheme in the key, because they are not interchangeable.

When one scan finds the same repo under several schemes, keep `https`, then
`git`, then `http`. An existing entry's URL is never rewritten.

## Commands

```
git fetchview add merges [-n N] [<rev-range>]
git fetchview add maintainers [<path>]
git fetchview add url [--from-file <path|->] [<url>...]
git fetchview list
git fetchview remove <url-or-label>
```

Options shared by every `add`:

- `--file <path>`: write to this file instead of the default, and register it.
- `--global`: register the file in `~/.gitconfig` instead of the local config.
  Requires `--file`, since the default file is local.
- `--all`: add every new candidate without opening the picker.
- `--dry-run`: print what would be written and change nothing.

### Where `add` writes

- Default file: `fetchview.remotes` in the common git dir, that is
  `.git/fetchview.remotes`.
- If the target file is not already registered, register it with
  `git config --add fetchview.remotes <path>` in the chosen scope, local unless
  `--global`. Already-registered paths are not added twice.
- The file is created if needed and rewritten atomically (write a temporary
  file in the same directory, then rename).
- Existing lines, comments and order are kept. New entries are appended. When
  a candidate matches an existing entry by key, only its tags are merged into
  that line.

### `add` flow

Every source follows the same steps:

1. The source scans and returns candidates.
2. Invalid URLs are dropped. Duplicates collapse by key, and tags merge.
3. Candidates already present in any registered file are marked as present.
4. With `--all`, the new ones are written. Otherwise the multi-select picker
   opens with the new ones selectable.
5. The chosen entries are written, and a one-line summary prints: added,
   already present, rejected.

Without a terminal and without `--all`, `add` fails with a message saying so,
rather than hanging.

### Sources

**merges**: runs `git log --merges --format=%s [-n N] <rev-range>`, default
range `HEAD`. For each subject, take the text after the last ` of ` as the
URL token, up to the next whitespace. This handles:

```
Merge tag 'net-6.12' of git://git.kernel.org/pub/scm/linux/kernel/git/netdev/net
Merge branch 'for-linus' of https://git.kernel.org/pub/scm/.../foo.git
Merge git://git.kernel.org/pub/scm/.../foo.git
```

Subjects with no URL (`Merge remote-tracking branch 'a/b'`) are skipped
silently. Tag: `merge`. The log can be very large, so read its output as a
stream.

**maintainers**: reads the file (default `MAINTAINERS` at the worktree root)
and takes `T:` lines of the form `T:<tab>git <url> [branch]`. The branch is
ignored. Other forms (`quilt`, `hg`, `git` with no URL) are skipped. Tag:
`maintainers`.

**url**: takes URLs from arguments, or from `--from-file` (one per line,
`-` for stdin; the same `#` comment rule applies). Tag: `manual`.

### `list` and `remove`

`list` prints `label<TAB>url<TAB>tags<TAB>file` for every entry in every
registered file.

`remove` matches by key or by exact label. If a label matches more than one
entry, it fails and lists them. It removes the entry from every registered file
that has it and reports which files changed.

## Picker

The remote list is the real remotes first (in `git remote -v` order), then the
collected entries sorted by label.

- A real remote and a collected entry with the same key show once, as the real
  remote.
- A real remote row is `name  url`. A collected row is `label  url  [tags]`, so
  `/maintainers` or `/net-next` filters on the tags and label as it does today.
- Choosing a row works as before: ref list, fetch, `tig`. The trail already
  uses the URL.
- Warnings from reading files (bad line, missing file) show in the status line.

## Multi-select picker

A second mode of the existing list, used only by `add`. It uses the same
keys as the main picker, plus:

| key     | action |
|---------|--------|
| `Space` | toggle the row under the cursor |
| `a`     | toggle all visible rows (so it respects the `/` filter): check them all, or uncheck if all were checked |
| `Enter` | confirm and write the checked entries |
| `q`     | quit and write nothing |

Rows already present show `(have)` and cannot be toggled. The status line shows
`N checked of M`. `Esc` does nothing at the top level, as elsewhere.

This is the one place `Enter` does not mean "select and go to the next level".
It confirms the whole selection, because a multi-select has no single row to
select.

## Code layout

New library modules:

- `remotes::entry`: `Entry`, URL validation, key, label.
- `remotes::file`: parse, render, merge, atomic write.
- `remotes::registry`: read the pointers with `git config`, load all files,
  register a path.
- `remotes::source`: the `Source` trait (`name()`, `scan() -> Vec<Candidate>`)
  and `merges`, `maintainers`, `manual`.
- `tui::select`: multi-select state, built on `tui::list::List` with a set of
  checked indexes.

Changed:

- `git::Remote` gains `tags: Vec<String>`. For a collected entry `name` is the
  label. `tui::app::App` takes the combined list.
- `cli` gains `add`, `list` and `remove`.
- `error::Error` gains variants for a bad remotes file, an invalid URL, and
  "needs a terminal".

The pure parsers (`parse_merge_subject`, `parse_maintainers`, `parse_file`,
`validate_url`) take `&str` and return values. They do no I/O so they can be
unit-tested and fuzzed.

## Testing

- Unit tests with fixtures taken from real kernel merge subjects and
  `MAINTAINERS` entries, including the odd forms: no `of`, `into` suffixes,
  `quilt`, `hg`, URLs with a branch.
- Unit tests for key and label derivation, scheme-insensitive dedupe, the
  https-over-git preference, and rejection of `ext::`, `file:`, leading `-`
  and embedded whitespace.
- Unit tests for file round-trip: comments and order kept, tags merged,
  appended entries.
- State tests for the multi-select: toggle, `a` with a filter, `(have)` rows
  not togglable, `q` writes nothing.
- An integration test in a temporary repo that registers a file with
  `git config`, checks relative-path resolution from local and global config,
  and checks that `add --all --dry-run` changes nothing.
- Fuzz targets for the four parsers, next to the existing two.

## Decisions to confirm

- The config section is `fetchview`, not `filterview`.
- Tab-separated lines for the files, not git-config syntax.
- Scheme-insensitive dedupe across `http`, `https` and `git`.
- `Enter` confirms in the multi-select.
- lore.kernel.org and remembered refs are deferred.
